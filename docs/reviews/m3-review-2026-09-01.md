## 1. Verdict

**M3 is a strong production-operations implementation candidate, but it is not yet accepted.**

The architecture remains sound. The implementation correctly preserves the accepted M1/M2 execution model while adding the intended M3 operational surfaces:

- durable Agent installation identity and Node binding;
- local process locks;
- credential issue/list/revoke and reload;
- bounded Run pagination;
- live log following and retention;
- SQLite online backup and offline restore normalization;
- bounded status/metrics projections;
- doctor diagnostics;
- structured logging and systemd hardening.

No redesign is required.

The remaining work is a focused M3 hardening pass around crash-safe local files, credential issuance failure handling, complete log streaming, late retransmission after retention, bounded metrics, and restore rollback safety.

Do not begin M4.

## 2. What is already good

### Agent fencing

The Agent installation ID is durable across ordinary restart.

The Server binds each Node to one durable Agent installation identity and rejects a different installation with \`agent_binding_conflict\`.

Binding replacement is explicit and checks for potentially executing work.

### Local single-instance locks

Server and Agent use non-blocking advisory locks around their correctness state.

Offline Server maintenance and Agent spool reset use the same lock domains.

### Credential model

New Agent credentials are generated from the operating-system CSPRNG with 256 bits of random material.

Only digests are persisted.

Issue responses are marked \`Cache-Control: no-store\`.

Revocation is idempotent and legacy inline credentials do not resurrect a Node that already has credential history.

Agent/operator token reload preserves the previous token when reload fails.

### Log lifecycle

Retention only selects complete terminal Attempt logs.

Expiration metadata is committed before unlink, so an expire-before-unlink crash is recoverable.

Expired logs keep Run/Attempt history and return \`410 log_expired\`.

Unexpected file absence remains a distinct diagnostic failure.

The per-Attempt log lock registry now uses weak references rather than growing one strong lock per historical Attempt.

### Backup

Online backups use SQLite's Online Backup API rather than copying the live WAL-mode main database file.

A backup is integrity-checked, checksummed, fsynced, atomically renamed, and accompanied by an atomically published manifest.

Temporary/incomplete objects are not listed as backups.

Corruption verification and concurrent-write backup behavior are tested.

### Restore normalization

Offline normalization converts stale execution state into terminal restore outcomes and clears retry/process diagnostics without touching scheduler configuration or mirror data.

### Status and diagnostics

Public status is opt-in and sanitized.

The implementation tests a status projection against deliberately secret-bearing configuration and confirms source/path/secret data is absent.

Doctor is read-only and uses stable check IDs.

### systemd

Server hardening is appropriately stronger than Agent hardening.

The Agent is not over-restricted in ways that would obviously break rsync/custom process execution.

## 3. Release blockers

### B1 — stale Agent-ID temporary file can permanently block restart

Location:

~~~text
apps/lmt-agent/src/lib.rs::load_or_create_installation_id
~~~

First-install creation uses a fixed temporary path:

~~~text
agent-id.tmp
~~~

opened with \`create_new(true)\`.

Crash window:

~~~text
create agent-id.tmp
write + fsync
<process/power failure before rename>
~~~

On next startup:

- final \`agent-id\` is absent;
- \`agent-id.tmp\` still exists;
- \`create_new\` fails;
- Agent cannot recover without manual deletion.

This directly contradicts M3's durable-identity/restart objective.

The Agent process lock is already held before identity creation, so recovery can be made safely.

**Required fix:** make installation-ID creation crash-recoverable. Use a unique temporary file or safely recover/remove a stale fixed temporary file under the Agent lock. Validate any recovered final ID before use.

Add a regression test that pre-creates the crash artifact and proves normal startup recovers.

### B2 — credential issue can leave an active credential whose raw secret is lost

Location:

~~~text
apps/lmt-cli/src/main.rs
CredentialCommand::Issue / write_secret
~~~

Current order:

~~~text
Server creates active credential and returns raw token once
-> CLI attempts local token-file write
~~~

If local persistence fails because:

- target already exists;
- parent is absent/unwritable;
- fixed \`.tmp\` already exists after a prior crash;
- disk write/fsync/rename fails;

the Server credential remains active, but the one-time raw token may be lost.

This creates an unusable active credential that must be discovered/revoked manually.

The fixed local \`.tmp\` path also has the same stale-temp crash problem as B1.

**Required fix:**

1. preflight obvious local destination failures before asking the Server to issue;
2. use crash-safe unique/recoverable temporary-file publication;
3. if local persistence fails after issuance, best-effort revoke the newly created credential;
4. if cleanup revocation also fails, print the credential ID and an explicit manual-revocation instruction without printing the raw token.

Add tests for local write failure and cleanup behavior.

### B3 — non-follow log command silently truncates logs larger than one API chunk

Locations:

~~~text
apps/lmt-cli/src/main.rs
apps/lmt-server/src/lib.rs::read_log
~~~

Server defaults one log response to 65,536 bytes.

\`lmt run logs <id>\` without \`--follow\` performs only one GET.

Therefore a 1 MiB completed log can silently display only its first 64 KiB.

This violates the operator meaning of "show this Run log".

At the other extreme, \`--follow --output json\` currently accumulates every byte into one in-memory \`Vec\`, which is unbounded for multi-GB sync logs.

**Required fix:** use one shared chunked log reader.

- non-follow: repeatedly fetch offsets until current complete EOF;
- follow: repeatedly fetch offsets and wait at incomplete EOF;
- human/raw streaming must remain O(chunk) memory;
- machine-output behavior must also have a bounded-memory contract; do not buffer an arbitrarily large log merely to wrap it as one JSON string.

Add a completed log test larger than 64 KiB and a bounded-memory/streaming test or equivalent contract test.

### B4 — a late Agent retransmission can recreate an intentionally expired log file

Locations:

~~~text
apps/lmt-server/src/lib.rs::append_log
crates/lmt-store/src/lib.rs::update_log_metadata
~~~

Retention correctly does:

~~~text
expired_at_ms = now
-> unlink log file
~~~

But a later Agent retransmission does not check \`expired_at_ms\`.

Possible sequence:

~~~text
Server received complete log
terminal/log ACK to Agent was lost
Agent remains offline for a long time
retention expires and deletes central log
Agent reconnects and retransmits old log bytes
Server recreates the expired file
API still reports 410 because metadata is expired
~~~

This can cause a large unexpected disk spike and violates retention finality.

**Required fix:** once a log is intentionally expired, upload retransmission must not recreate its file.

The Server should acknowledge the historical logical offset/completion in a way that lets the Agent retire its spool safely, while preserving \`expired_at_ms\`.

Add a late-retransmission-after-expiry test.

### B5 — the stored-log-bytes metric still has O(history) scrape cost

Location:

~~~text
crates/lmt-store/src/lib.rs::operational_counts
~~~

The M3 implementation removed the old full \`list_runs()\` metrics path, but still computes:

~~~sql
SELECT COALESCE(SUM(stored_bytes),0)
FROM attempt_logs
WHERE expired_at_ms IS NULL
~~~

If automatic log retention is disabled, \`attempt_logs\` grows with historical Attempts forever.

Every Prometheus scrape can therefore scan historical log metadata.

This violates the frozen M3 rule:

> Prometheus scrape cost must not scale by loading/scanning total historical Run/Attempt history.

The current 10,000-Run metrics test does not populate 10,000 \`attempt_logs\` rows, so it does not exercise this path.

**Required fix:** make current stored-log-byte reporting O(1) or otherwise bounded per scrape, for example through transactionally maintained aggregate state or an equivalent design.

Strengthen the scale test with a large Attempt-log history and verify the metrics path does not depend on a full-history aggregate scan.

### B6 — offline restore destroys old WAL sidecars before the previous database is safely archived

Location:

~~~text
apps/lmt-server/src/main.rs::restore
~~~

Current restore order includes:

~~~text
verify/normalize new restored DB
delete current lmt.db-wal / lmt.db-shm
rename current lmt.db to archive
install new DB
~~~

If the previous Server died uncleanly, committed state may still live in the current WAL.

Deleting the WAL before preserving the old database set can make the archived "pre-restore" database incomplete.

Worse, if installation of the new database then fails, rollback restores only the old main DB file, not the deleted WAL state.

**Required fix:** preserve the previous database state as a coherent recovery unit before installing the replacement.

Acceptable approaches include safely checkpointing the old database under the exclusive Server lock before archival, or archiving/restoring the main database and relevant sidecars as one unit.

A stale old WAL must also never be paired with the new restored main database.

Add failure-injection tests for restore installation failure and an old database with committed WAL content.

### B7 — backup-last-success metric loses truth on every Server restart

Location:

~~~text
apps/lmt-server/src/lib.rs::AppMetrics
~~~

\`lmt_backup_last_success_timestamp_seconds\` is only an in-memory atomic updated when the current process creates a backup.

After Server restart it returns zero even if the configured backup directory contains a valid recent backup.

This makes backup-recency alerting produce false alarms after every restart.

The backup manifests already provide persistent source-of-truth data.

**Required fix:** initialize or derive last successful backup timestamp from persistent manifests on startup/scrape, while keeping backup creation updates cheap.

Add a restart/reinitialize test with an existing backup directory.

## 4. Release-gating test gap

### T1 — restore workflow is tested in components, not as the full maintenance boundary

The current suite covers:

- Server lock primitive;
- backup integrity/corruption;
- Store restore normalization;
- Agent spool reset and identity preservation.

However, M3's implementation plan required a restore workflow integration test with stopped/locked components.

While fixing B6, add a test covering the actual local restore maintenance path:

~~~text
Server lock exclusion
-> verified backup
-> old database preservation
-> replacement installation
-> restore normalization
-> reopened Store cannot redeliver stale execution
~~~

The Agent spool-reset test can remain separate as the Agent-side quiescence proof.

## 5. Non-blocking engineering debt

### N1 — human CLI output is functional but not yet polished tables

Human output is currently compact JSON-ish rows / key-value lines.

It is readable and JSON mode is explicit, so this does not block M3 correctness.

Before community-release polish, add command-specific tables for Run/Node/Mirror lists if operator feedback shows value.

### N2 — doctor may be intentionally noisy for merely-due Mirrors

Any due Mirror currently produces a warning, which makes doctor exit 8.

That may be useful during a controlled trial, but production experience should decide whether "due" versus "overdue" needs a separate threshold.

### N3 — doctor scans log metadata/files

Doctor is explicitly operator-invoked rather than a scrape endpoint, so a heavier consistency scan is acceptable for M3.

If real histories make it slow, add a fast/default mode later rather than complicating the current release.

### N4 — backup listing trusts manifest presence until explicit verify

\`backup list\` intentionally lists published database+manifest pairs without re-hashing every backup.

This keeps listing cheap.

\`backup verify\` remains the integrity operation.

## 7. M3 acceptance criteria after hardening

M3 can be accepted when:

1. Agent installation-ID creation recovers from a stale/crashed temporary publication;
2. credential issuance cannot silently leave an active unusable credential after local file-write failure;
3. completed logs are fully streamed beyond 64 KiB and follow/machine modes remain bounded-memory;
4. expired logs cannot be recreated by late retransmission;
5. Prometheus stored-log-byte metrics have bounded history cost;
6. restore preserves the previous main/WAL state safely across replacement failure;
7. backup last-success metric survives Server restart from persistent backup metadata;
8. the real offline restore maintenance path is integration-tested;
9. all existing M1/M2/M3 tests remain green;
10. no M4/M5 features are introduced.

After these fixes, perform M3 review round 2 before beginning a controlled production trial.

## 8. Overall assessment

The difficult architectural work is already correct.

Do not replace SQLite, add a broker, introduce a distributed controller, or redesign Agent execution.

The remaining work is narrow production hardening around crash-safe publication, long-log streaming, retention finality, persistent observability, and disaster-recovery rollback.
