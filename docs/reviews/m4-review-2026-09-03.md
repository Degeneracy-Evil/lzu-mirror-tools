## P0-1 — full-writer fence is pathname-based for Direct work

Frozen D071 requires an abandoned publication fence to block **all LMT writers
for that Mirror on the old Node**, including Direct mode.

Current Atomic specs carry `publication.mirror`, but Direct
`ProcessRunSpec` has no Mirror identity. Agent Direct admission therefore
infers the fenced Mirror only when:

~~~text
fenced Atomic published_dir == incoming Direct target_dir
~~~

The existing test explicitly proves that a Direct writer to the old pathname is
blocked while an unrelated target pathname is admitted.

That is weaker than the frozen contract.

Counterexample:

~~~text
Mirror demo on n01
Atomic target = foo
-> visibility committed
-> durability fails
-> operator abandon/fence

later:
same Mirror demo becomes Direct with target = bar
-> Direct RunSpec has no Mirror identity
-> old n01 fence cannot associate bar with demo
-> writer may be admitted
~~~

Required fix:

- carry explicit Mirror identity for M4 execution admission independently of the
  Atomic publication extension;
- preserve the exact M3 StartAttempt/Direct RunSpec wire shape for M3 Agents;
- use Mirror identity, not target pathname, for full-writer fence admission;
- keep unrelated Mirrors runnable.

A small optional M4 StartAttempt execution-identity field, conditionally omitted
for M3 Agents, is preferable to weakening legacy Direct RunSpec compatibility.
Do not infer capability from arbitrary version strings.

Required tests:

1. fenced Mirror + Direct same Mirror + changed target => rejected;
2. fenced Mirror + unrelated Mirror => allowed;
3. Move away/back or later target change cannot bypass the old-Node fence;
4. M4 Server -> M3 Agent StartAttempt remains the frozen M3 wire shape.

## P0-2 — installer regresses accepted /etc/lmt traversal layout

The controlled production trial T002 froze this layout:

~~~text
/etc/lmt/               root:root      0755
server.toml             root:lmt       0640
operator.token          root:lmt       0640
agent.toml              root:lmt-agent 0640
agent.token             root:lmt-agent 0640
~~~

Current `install.sh` creates `/etc/lmt` with mode `0750` in both Server and
Agent installation paths.

On a real host this prevents the independent `lmt-agent` service user from
traversing `/etc/lmt`, even though its own files are group-readable. This
reintroduces a production-trial failure that M4 installer automation was meant
to eliminate.

Required fix:

- always keep shared `/etc/lmt` as `root:root 0755`;
- keep service-specific files protected with their accepted owners/modes;
- make repeated server/agent/all/upgrade installation preserve this invariant.

Required tests:

- staged permission assertions;
- preferably a real service-user readability/traversal check when the
  integration environment permits it.

## P1 — offline abandon does not immediately reconcile the public Run

The frozen safety property is preserved: abandon durably writes
`abandoned_fenced` before any possible Server terminal event.

However the M4.10 implementation plan also required the local maintenance
command to attempt Server terminal reconciliation after the durable fence, and
to leave the evidence pending only when the Server is unavailable.

Current local `publication abandon` returns after durable local fencing. The
public Run remains non-terminal until the Agent daemon is started and normal
reconciliation later succeeds.

Preferred fix:

1. persist the exact durable fence;
2. attempt one terminal reconciliation using configured Server/token;
3. if unavailable, retain the fence and report clearly that Server
   reconciliation is pending;
4. never clear the fence merely because the terminal report succeeded.

This is operationally important because the purpose of explicit abandon is to
release a permanently stuck public Run for controlled recovery/Move.
