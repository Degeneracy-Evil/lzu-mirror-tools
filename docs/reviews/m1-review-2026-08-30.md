# M1 Code Review — 2026-08-30

> Historical blocking review. The findings were addressed by the M1 hardening pass and M1 was subsequently accepted in [M1 Code Review Round 2](m1-review-round2-2026-08-30.md).

Reviewed implementation head:

```text
409ea99502dcc56f0abdbec110cd9529629a4498
```

Review scope:

- architecture/dependency boundaries;
- configuration semantics;
- central SQLite behavior;
- Server-Agent protocol and idempotency;
- process supervision;
- Run log transport;
- systemd packaging;
- M1 release-gating tests.

## 1. Verdict

**M1 implementation is structurally sound but is not yet accepted as M1-complete.**

The implementation follows the intended high-level architecture closely and does not require a rewrite. However, several correctness and operational issues violate explicit M1 release gates, especially around process supervision, centralized Run logs, duplicate StartAttempt handling, and fault-injection coverage.

The next development step should be a focused **M1 hardening pass**, not M2 scheduler work.

## 2. What is already good

The following design goals are implemented well enough to preserve:

- the planned three library crates and three binaries exist;
- `lmt-core` remains free of Axum/SQL/database/runtime infrastructure;
- `lmt-protocol` is transport-neutral;
- Agents never open the central database;
- configuration bundles are canonicalized and hashed;
- config apply is transactional and revision-checked;
- manual Run request IDs are idempotent;
- SQLite has a partial unique index enforcing one active Run per Mirror;
- Agent authentication derives Node identity from bearer credentials rather than request JSON;
- Attempt event sequence handling rejects state regression;
- central log append verifies overlapping retransmitted bytes;
- systemd units use restart-on-failure and the Agent unit uses control-group killing;
- formatting, Clippy, and ordinary workspace tests are wired into CI.

These are useful foundations. Fixes should preserve them.

## 3. Release blockers

### B1 — Agent does not actually capture child stdout/stderr

Location:

```text
apps/lmt-agent/src/main.rs
```

The process is spawned without configuring stdout/stderr pipes and later consumed through `wait_with_output()`.

The expected M1 behavior is:

```text
sync process stdout/stderr
        -> Agent
        -> central Run log
        -> lmt run logs
```

The current implementation can leave stdout/stderr inherited by the Agent process instead, so the generated central Run log may be empty even when the child emitted output.

This breaks the M1 observable-failure acceptance scenario.

**Required direction:** implement explicit stdout/stderr capture and test through a real Server-Agent E2E path.

Do not fix this by simply piping both streams and buffering the whole process output with `wait_with_output()` for production mirror workloads. Long-running rsync output must be streamed/spooled incrementally with bounded memory.

### B2 — No real process-group supervision for timeout/cancellation

Location:

```text
apps/lmt-agent/src/main.rs
```

The implementation uses `kill_on_drop(true)`, but it does not establish a dedicated process group/session for the Attempt.

Therefore a child program that spawns descendants can leave descendants alive when only the direct child is killed by timeout or Agent-side cancellation logic.

This violates:

- no unmanaged writer after timeout;
- no orphan descendants after Agent failure/restart;
- whole-process-group cancellation semantics.

The systemd service-level `KillMode=control-group` helps when the **Agent unit itself** is stopped/restarted, but it does not replace per-Attempt process-group supervision while the Agent remains alive.

**Required direction:** every Attempt gets its own supervised Unix process group; timeout/cancel signals the group and waits/reaps correctly. Add a helper-process test that creates a grandchild.

### B3 — Duplicate StartAttempt race before durable ACCEPTED

Location:

```text
apps/lmt-agent/src/main.rs::start
```

The documented order is:

```text
receive
-> local validation
-> durably record ACCEPTED
-> start execution
```

Current behavior inserts the execution key in an in-memory `HashSet`, then spawns a task that writes the durable spool. A duplicate StartAttempt can arrive before the spool file exists.

When `max_concurrent_runs > 1`, the duplicate path may pass capacity checks. The return value of `active.insert(key)` is not used to reject an already-active key, so two execution tasks can be created for the same `(run_id, attempt_no)`.

This directly violates the strongest LMT idempotency invariant.

**Required direction:** serialize per-attempt acceptance and make durable ownership establishment atomic before execution. The in-memory active set may be an optimization/guard, but the durable spool is the recovery authority.

A concurrent duplicate-delivery test is required.

### B4 — Existing spool + conflicting spec hash is unsafe

Location:

```text
apps/lmt-agent/src/main.rs::start
```

If a spool already exists with a different `spec_hash`, the current code mutates that spool to `Rejected` and reports it.

If the existing Attempt is currently Running, its process may continue while its durable state is rewritten as Rejected.

That creates a dangerous contradiction:

```text
server believes Rejected
but writer may still be alive
```

**Required direction:** a spec-hash conflict for an existing execution key is a protocol-integrity error. Never overwrite a live/terminal attempt history to Rejected. Refuse the conflicting command, preserve the original execution record, surface a loud diagnostic, and keep the original ownership semantics intact.

### B5 — Agent systemd sandbox blocks the configured mirror root

Location:

```text
packaging/systemd/lmt-agent.service
config/agent.example.toml
```

The Agent unit uses:

```text
ProtectSystem=strict
```

while the example mirror root is:

```text
/srv/mirrors
```

The service only gains a writable state directory under `/var/lib/lmt-agent`; the mirror root is not separately allow-listed.

The packaged service can therefore be unable to perform its core job: writing mirror files.

**Required direction for v0.1:** keep the service simple and avoid duplicating `mirror_root` in a hidden systemd setting. Prefer a hardening profile whose writable-filesystem semantics are compatible with the normal Unix permissions of the dedicated `lmt-agent` user. If `ProtectSystem=strict` is retained, installation must generate/document an explicit writable-path override tied to the configured mirror root.

Also verify that start-limit directives are placed in the systemd section where they are actually effective.

### B6 — M1 release-gating E2E/fault tests are missing

The repository has unit/integration-style tests, but the M1 plan explicitly requires end-to-end fault scenarios.

Missing automated proof includes at least:

- Server + Agent success through HTTP;
- observable stdout/stderr failure through central log API;
- lost StartAttempt response;
- lost terminal-event acknowledgement;
- Agent crash with descendant cleanup;
- Server crash while Attempt continues;
- config reconciliation preserving history/data.

A green `cargo test` is useful but does not establish the distributed correctness contract.

**Required direction:** create a local E2E harness with temporary server DB/log/spool directories and helper executables. Normal CI must remain internet-independent.

M1 is not accepted until these scenarios run automatically.

### B7 — Config removal/disable can still dispatch stale Pending work

Locations:

```text
crates/lmt-store/src/lib.rs
docs/scheduler.md
```

Current config removal sets:

```text
managed = 0
```

but existing Pending Runs remain, and `poll_action` selects Pending Runs by owner Node without rechecking whether the Mirror is still managed/enabled.

Therefore:

```text
manual Run created while node offline
-> Mirror removed from authoritative TOML
-> node returns
-> old Run can still be dispatched
```

This contradicts authoritative desired-state semantics.

There is also a design nuance: once a StartAttempt has already been dispatched, the Server cannot safely assume it has not begun merely because the public Run still says Pending.

The design documents have been clarified in the same review commit:

- **undispatched** Pending work is cancelled on disable/remove;
- once an Attempt has been dispatched, config reconciliation does not revoke it implicitly;
- explicit cancellation protocol is required to stop dispatched work;
- disable/remove prevents new Attempts/retries.

Implementation must model this boundary explicitly enough to avoid guessing from public Run state alone.

### B8 — Empty-output Attempts never finalize central log metadata

Location:

```text
apps/lmt-agent/src/main.rs::reconcile
```

Log upload only occurs when a local log file exists and `log_offset < log.len()`.

For a successful command that emits zero bytes, no upload request is made, so the Server may never learn that the Attempt's log stream is complete.

**Required direction:** completion of a zero-byte log stream must be representable independently from uploading non-empty bytes.

### B9 — Durable spool is never retired

Terminal spool/log files remain indefinitely after result/log acknowledgement.

`resend_durable_results` repeatedly scans terminal records; if a log file exists, the condition continues to make the record eligible for reconciliation.

This violates the intended meaning of the Agent spool as temporary recovery state and will cause unbounded local accumulation over long-running mirror operations.

**Required direction:** define one safe cleanup condition:

```text
terminal event acknowledged
AND all log bytes/completion acknowledged
-> atomically retire/remove local spool artifacts
```

Test crash points around cleanup.

### B10 — Intermediate Attempt events are not durably retransmitted

Accepted/Running reports are attempted once and failures are ignored. The poll request also sends:

```text
running: []
```

unconditionally.

A lost Accepted/Running report can leave the Server viewing a long-running Attempt as Queued until a terminal snapshot eventually arrives.

This is not necessarily a duplicate-execution bug because the Agent spool can still reject a duplicate StartAttempt, but it breaks the intended observed-state/reconciliation model and complicates restart reasoning.

**Required direction:** either durably track/report the highest unacknowledged event state, or use the poll's owned/running Attempt summaries as reconciliation evidence. Do not rely on terminal success eventually repairing all intermediate state.

## 4. Architecture issues to fix before M2

### A1 — `lmt-store` owns too much domain behavior

Current `lmt-store` includes:

- TOML parsing for generations;
- placeholder resolution;
- RunSpec compilation;
- dispatch selection;
- Attempt transition decisions;
- Attempt terminal -> Run terminal projection.

This is more than persistence.

The documented dependency model says:

```text
lmt-core  = domain meaning / transition rules / compilation
lmt-store = persistence / transactions
server    = orchestration
```

Before adding scheduler/retry behavior in M2, refactor this boundary or `lmt-store` will become the application's business-logic center.

Recommended direction without adding new crates:

- move pure Mirror-generation -> RunSpec compilation into `lmt-core`;
- move transition/projection logic into `lmt-core`;
- Server service layer decides which domain operation to perform;
- Store executes transactional persistence primitives and invariant checks.

Do this before scheduler complexity lands.

### A2 — Agent and Server are already monolithic files

Current files are approximately:

```text
apps/lmt-agent/src/main.rs   ~500 lines
apps/lmt-server/src/lib.rs   ~700 lines
crates/lmt-store/src/lib.rs  ~900 lines
```

This is not a crate-count problem. Do **not** create more crates.

Split modules inside the existing crates along the boundaries already documented:

Agent:

```text
config / client / poll / executor / supervision / spool / log_upload / recovery
```

Server:

```text
api / services / auth / logs / app
```

Store:

```text
migrations / config_repo / node_repo / run_repo / attempt_repo / log_index_repo
```

The purpose is testability and ownership, not abstraction for its own sake.

## 5. High-priority correctness/quality issues

These do not individually require a redesign but should be resolved during the same hardening pass where practical.

### Q1 — Empty mirror target is accepted

`target = ""` passes current path validation and can collapse the effective target onto `mirror_root`.

Reject empty targets.

### Q2 — Placeholder validation is incomplete

Placeholders are resolved in `program`, `args`, and `cwd`, but validation currently checks only args/cwd.

Use one strict placeholder parser/validator for every supported field. Reject malformed unmatched braces rather than silently carrying them through.

### Q3 — Nested Agent config silently accepts unknown fields

Top-level Agent config denies unknown fields, but nested structs do not consistently do so.

For a hand-authored TOML operations tool, typos should fail closed.

### Q4 — Queued -> terminal snapshot can produce no Run start timestamp

The Server intentionally accepts terminal snapshots that skip missing intermediate network events. That is correct.

However, if a terminal event arrives while the stored Attempt is still Queued, the final Run can become terminal while `started_at` remains null.

Terminal snapshots should contain enough information for the Server to reconstruct the Run's observed start time when available.

### Q5 — Synchronous SQLite work runs directly on async worker threads

`rusqlite` operations are serialized behind a standard mutex and invoked from Axum async handlers.

This is acceptable for a tiny M1 prototype, but it is a clear pre-production latency risk, especially when transactions or DB busy waits block Tokio worker threads.

Before M2/production load, route SQLite work through a dedicated blocking boundary/DB worker rather than converting the whole architecture to async SQL.

### Q6 — Global log mutex serializes all Node/Attempt uploads

One global async mutex protects every central log append.

Correctness is simple, but unrelated Attempts unnecessarily block one another.

A per-log/per-Attempt lock or append ownership model will scale better without changing protocol semantics.

### Q7 — Metrics endpoint is only a liveness scalar

`/metrics` currently exposes essentially:

```text
lmt_up 1
```

Keep this acceptable for early bootstrap, but M1 hardening should add enough metrics to diagnose:

- Agent liveness;
- active/pending Runs;
- Attempt results;
- API/log upload failures.

Do not build a monitoring platform; just expose useful control-plane facts.

### Q8 — Migration framework is only sufficient for schema version 1

The current migration function executes one idempotent schema file and records version 1.

That is fine before the first schema change. Before introducing schema version 2, create ordered versioned migrations with tests from every supported previous schema.

### Q9 — Type safety is only partially used

Typed identifiers exist in `lmt-core`, but many protocol/store fields remain arbitrary strings, and `ProcessRunSpec.runner` is a String.

This is not a release blocker, but new M2 code should avoid expanding stringly-typed domain state. Tighten types as boundaries are refactored.

### Q10 — Credential configuration semantics need a future cleanup

Server startup upserts configured Agent tokens but does not revoke credentials removed from `server.toml`.

Enrollment/rotation UX is already an open design item; avoid treating current bootstrap configuration as a finished credential-management model.

## 6. M1 acceptance criteria after hardening

M1 can be accepted when all of the following are true:

1. stdout/stderr reaches central Run logs through real process execution;
2. process-group timeout/cancellation leaves no descendants;
3. concurrent duplicate StartAttempt cannot produce duplicate execution;
4. conflicting spec hash cannot overwrite a live execution record;
5. packaged Agent can actually write configured mirror data;
6. config remove/disable obeys the clarified dispatch boundary;
7. empty logs reach a durable complete state;
8. acknowledged spool/log records are safely retired;
9. event reconciliation survives dropped intermediate acknowledgements;
10. release-gating E2E fault scenarios run automatically;
11. architecture logic begins moving out of `lmt-store` before M2 scheduler work.

After these are fixed and reviewed, proceed to M2.

## 7. Review principle

The implementation is promising because the difficult top-level architecture decisions survived contact with code.

The correct response to the issues above is **not** to add a message broker, replace SQLite, switch to gRPC, or introduce a framework. Most problems are local correctness boundaries inside the intentionally small architecture.

Keep the architecture small and make the execution/recovery semantics rigorous.
