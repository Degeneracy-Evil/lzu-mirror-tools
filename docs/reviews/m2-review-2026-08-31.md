## 1. Verdict

**Historical status:** this review blocked the first M2 candidate. All blockers were resolved by hardening baseline `7ad3886c1c11d011ae6fd76df2fa6ecc1b87bdaf`; see [M2 Code Review Round 2](m2-review-round2-2026-08-31.md).

The major M2 architecture is implemented correctly:

- one async single-connection SQLite Store;
- ordered schema migrations;
- persisted coalesced schedule due intent;
- Scheduled Run materialization on Agent poll;
- same-Run retry deadlines;
- capacity-aware dispatch;
- durable cancellation and Cancel-before-Start tombstones;
- built-in rsync compiled to the generic process runner;
- M1 regression behavior retained.

No architectural rewrite is required.

However, several correctness and release-gating issues remain. The next step is a focused M2 hardening pass, not M3.

## 2. What is already correct

### Persistence boundary

The Store uses tokio-rusqlite and still owns one authoritative SQLite connection. No pool, PostgreSQL, or second source of truth was introduced.

### Migration structure

The previous M1 schema was moved to migration 0001 and M2 schema additions are migration 0002.

Direct comparison with the accepted M1 SQL shows the schema is compatible; the principal textual difference is removal of idempotent IF NOT EXISTS clauses in the fresh migration file.

Tests cover migration, rollback, and future-version refusal.

### Scheduler model

Schedule occurrences persist a coalesced due marker rather than one queued Run per tick.

Scheduled Runs materialize only during eligible owner-Agent polling and use the current Mirror generation.

Interval/cron calculations live in lmt-core.

### Retry model

Failed, TimedOut, and Interrupted Attempts can schedule a persisted retry_due_at.

Attempt N+1 is created only after the deadline on an eligible Agent poll.

The Run ID remains unchanged.

### Cancellation protocol

CancelAttempt includes spec_hash.

The Agent can persist a cancellation tombstone before seeing StartAttempt.

Matching delayed Start is suppressed; conflicting hash is treated as protocol-integrity failure.

### rsync boundary

Rsync stays outside Agent semantics and compiles to the existing ProcessRunSpec/native executor.

Source trailing-slash form is preserved.

## 3. Release blockers

### B1 — cancelling an already-terminal Run mutates history

Location:

~~~text
crates/lmt-store/src/lib.rs::request_cancellation
~~~

Current order is effectively:

~~~text
read Run
UPDATE cancel_requested_at_ms = COALESCE(...)

if run.state.is_terminal() {
    return Run
}
~~~

Therefore:

~~~text
Run Succeeded at 10:00
operator runs: lmt run cancel <id> at 11:00
~~~

adds a cancellation timestamp that never existed during execution.

This violates the documented API rule that cancelling a terminal Run returns it unchanged.

It also makes historical diagnosis misleading.

**Required fix:** test terminal state before persisting cancellation intent. Terminal Runs must be field-semantically unchanged by later cancel requests.

Add explicit tests for Succeeded, Failed, TimedOut, and Cancelled terminal Runs.

### B2 — Cancel-before-Start tombstones are never retired

Locations:

~~~text
apps/lmt-agent/src/spool.rs::ready_for_cleanup
apps/lmt-agent/src/lib.rs::reconcile_all
~~~

ready_for_cleanup requires spec.is_some().

A cancellation tombstone deliberately has:

~~~text
spec = None
state = Cancelled
~~~

so even after the Server has acknowledged the terminal Cancelled event and empty log completion, the tombstone cannot retire.

Consequences:

- permanent local spool-file leak;
- every tombstone is scanned by reconcile_all every 200 ms forever;
- long-lived Agents accumulate periodic filesystem work proportional to historical cancel-before-Start events.

The tombstone is necessary until cancellation is reconciled, not forever.

**Required fix:** after the terminal cancellation event and log completion are both acknowledged by the Server, the tombstone may retire.

Keep the existing pre-ack delayed-Start suppression test and add post-ack tombstone cleanup coverage.

### B3 — normal direct-child completion can leave Attempt descendants alive

Location:

~~~text
apps/lmt-agent/src/executor.rs
~~~

The executor terminates the Attempt process group for timeout, Agent shutdown, and explicit cancellation.

But on child.wait() normal success/failure it does not verify or clean remaining processes in the same Attempt process group before terminalizing the Attempt.

A custom command can:

1. spawn a background descendant;
2. redirect or close inherited stdout/stderr;
3. let the direct child exit;
4. keep the background process alive.

LMT can then mark the Attempt Succeeded/Failed while the descendant is still alive.

Dangerous state:

~~~text
Run 1 terminal
old descendant still writing mirror data
Run 2 later starts
=> two writers
~~~

This violates the real one-writer safety model.

**Required fix:** before a normal Succeeded/Failed terminal result is persisted, ensure no ordinary descendants remain in the Attempt's supervised process group. Remaining descendants must be terminated/reaped according to the process-runner ownership contract.

Add a regression test using a child that starts a background process with stdout/stderr redirected away and exits immediately.

Do not solve this by killing the entire Agent service.

### B4 — semantic metrics are not idempotent under event retransmission

Location:

~~~text
apps/lmt-server/src/lib.rs::event
~~~

The Store correctly de-duplicates already-applied Attempt events by event sequence.

The HTTP handler nevertheless increments terminal/retry counters after every successful event request, including duplicate retransmissions.

The accepted protocol explicitly allows:

~~~text
Server applies terminal event
HTTP acknowledgement is lost
Agent retransmits the same event
~~~

Current behavior can count one semantic Attempt completion or retry more than once.

Affected counters include:

- lmt_attempts_terminal_total;
- lmt_retries_scheduled_total.

**Required direction:** return whether the event caused a newly applied transition and whether a retry was newly scheduled. Increment semantic counters only for newly applied semantic events.

Also decide whether cancellation metrics count requests or semantic cancellation intents, and test repeated idempotent cancellation accordingly.

## 4. Release-gating test gaps

### T1 — scheduler is not exercised through the full Agent E2E path

The M2 real-process E2E matrix covers retries, restart during retry delay, disable during retry, Interrupted retry, capacity, active cancellation, and local rsync.

Scheduler behavior is covered at domain/Store/Server-service level with deterministic time, but the frozen M2 plan explicitly required a real vertical slice:

~~~text
schedule due
-> durable due intent
-> Agent poll
-> Scheduled Run materialization
-> real process execution
-> terminal Run
~~~

Add at least one deterministic interval E2E vertical slice. Cron E2E is preferred as well.

Do not use real minute sleeps.

### T2 — Cancel-before-Start lacks the network fault path

The Agent unit test correctly proves local tombstone behavior.

The E2E proxy does not currently force:

~~~text
Start dispatch recorded
Start response lost before Agent acceptance
operator cancels
Agent receives cancellation
command never executes
~~~

This was an explicit M2 fault scenario.

Add a proxy/harness case that drops a StartAttempt response, then cancels and verifies zero command executions.

The direct delayed-Start unit test should remain.

### T3 — DST test does not cover wildcard/step behavior

The current core test checks fixed-time spring-forward and fixed-time fall-back behavior.

The M2 contract also distinguishes wildcard/step jobs during DST transitions. Croner itself documents separate fixed-time versus wildcard/interval DST handling, so both categories need tests.

Add deterministic tests for:

- wildcard/step through spring-forward;
- wildcard/step through fall-back.

## 5. Non-blocking engineering debt

### N1 — metrics scrape scans full Run history

/metrics calls list_runs() and filters all historical Runs in memory for pending/running gauges.

As history grows, scrape cost becomes O(total Run history).

Before production trial, use aggregate COUNT queries or maintained gauges.

### N2 — per-Attempt log-lock registry still grows

The Server log-lock map is not evicted after completed logs.

This remains pre-production cleanup debt.

### N3 — cron semantic hash is canonical but not fully semantic

Some equivalent cron spellings/timezone aliases can still produce different hashes and reset schedule timing.

This is safe and may only cause an unnecessary reset. Do not build a complex cron-equivalence engine for M2.

### N4 — future migrations should use frozen previous-version fixtures

The current M1-to-M2 migration is compatible by direct schema comparison.

For future migrations, retain an exact previous-version schema fixture so migration tests cannot accidentally rewrite history.

## 7. M2 acceptance criteria after hardening

M2 can be accepted when:

1. terminal Run cancellation is truly non-mutating;
2. fully acknowledged cancellation tombstones retire safely;
3. normal direct-child completion cannot leave supervised descendants alive;
4. semantic Attempt/retry metrics are idempotent under duplicate event delivery;
5. deterministic scheduled execution reaches a real Agent/process in E2E;
6. Start-response-loss then cancellation is covered end-to-end;
7. fixed and wildcard DST behaviors are both tested;
8. all existing M1 and M2 tests remain green;
9. no M3 functionality is introduced.

After these items, a second M2 review should decide acceptance.

## 8. Overall assessment

The M2 architecture itself survived implementation well.

Do not redesign the scheduler, replace SQLite, add a broker, or introduce a new execution framework.

The remaining work is narrow hardening around lifecycle closure, idempotent observability, and fault-test completeness.
